## 1. Why this sub-project

A security audit of SP1/SP1.5 as merged on `main` (edd0706) left twelve findings open. Each one was re-verified in the code before being planned here (file:line below); none is already fixed. SP2+ build on the same auth, tenancy, queue and deployment layers, so the fixes land before the next feature plan. Three findings are design-level (ownership invariant, isolation-suite blind spots, notifications off the request path); the rest are configuration, CLI and supply-chain hardening.

### F1 — Reporter identity: super-admins only (audit log and organisation queue)

- **Threat.** AC-SAFE-02: « le professeur n'est pas informé de l'identité du signalant ». An org ADMIN who is reported reads `GET /workspaces/{wid}/audit-log` and sees `after.reporterUserId`; any OWNER/ADMIN can correlate reporter and reported through the audit log without the abuse queue's rules. And with the organisation queue naming the reporter, any org handler can tell the reported teacher who filed the report (Q1).
- **Decision (owner, Q1 — 2026-10-18).** The reporter's identity is visible to **super-admins only** (`/admin/abuse-reports` console). (1) The audit row of `abuse_report.created` carries `{ category, status, entityType, entityId }` only; `AuditService` gains a deny-list of keys that are never persisted in `before`/`after` (`reporterUserId`, `reporter`), next to the existing secret-key filter, so no future caller can reintroduce it. (2) The organisation-facing responses (`GET /workspaces/{wid}/abuse-reports`, `GET`/`PATCH …/{id}`) carry **no** `reporter` key at all (not `null`): `AbuseReportSchema` loses `reporter`; a new `AdminAbuseReportSchema = AbuseReportSchema.extend({ reporter: AbuseReporterSchema })` (+ `AdminAbuseReportsPageSchema`) types the `/admin/abuse-reports` responses, and `toView(row, scope)` adds `reporter` only for `scope.kind === 'admin'`. Nothing else org-facing names the reporter: the `abuse.new_report` email already does not (kept, asserted again in F12's worker tests); the `abuse_report.updated` audit row carries `{ status, assignedToUserId, resolution }` only. The reporter still sees their own reports through `GET /me/abuse-reports` (unchanged; no identity field needed). Web: the two super-admin components (`admin-abuse-reports-panel.tsx`, `admin-abuse-report-detail.tsx`) switch to the `Admin*` types; the i18n keys `admin.reports.reporter` / `admin.reports.openDetailFor` stay (super-admin console only). There is no organisation-facing abuse queue page in `apps/web` today, so no org UI column disappears; when SP2+ builds one, the contract already has no reporter.
- **Acceptance.** (a) `GET /workspaces/{wid}/audit-log` as the reported ADMIN and as the OWNER: no entry contains `reporterUserId` nor the reporter's id anywhere in its JSON; `AuditService.log({ after: { reporterUserId } })` stores an `after` without that key (unit test); existing abuse tests still see the row with the remaining fields. (b) As the org OWNER and as another ADMIN: the list, detail and `PATCH` responses of `/workspaces/{wid}/abuse-reports` have no `reporter` property and their JSON contains neither the reporter's id, first name nor last name; as a super-admin, `/admin/abuse-reports` and `/admin/abuse-reports/{id}` still return `reporter { userId, firstName, lastName }`; `GET /me/abuse-reports` unchanged. (c) `packages/contracts` tests: `AbuseReportSchema` has no `reporter` key, `AdminAbuseReportSchema` requires it. (d) The isolation suite (`apps/api/test/isolation`) and the web admin e2e (`admin.spec.ts`, which reads the reporter's name in the super-admin queue) stay green.

### F2 — Super-admin bootstrap and account pre-hijack

- **Threat.** An attacker registers `ops@example.com` first (the public teacher sign-up). The operator later runs the CLI with that email: the attacker's account, with the attacker's password, becomes `SUPER_ADMIN`; the CLI even marks the email verified.
- **Decision.** Creating is the default; **promoting an existing account requires all of**: the explicit flag `--promote-existing`, the account is `ACTIVE`, `emailVerifiedAt` is set (the CLI never sets it), and the `--password` given on the command line verifies against the stored argon2 hash (the operator proves they hold the account's credentials). Any other existing account → refusal with the reason (unverified email, password mismatch, non-active status) and exit code 1. `--password-stdin` reads the password from stdin so it never appears in shell history or `ps`. Promotion is still idempotent for an account that is already a super-admin (same checks).
- **Acceptance.** Spec tests: unverified existing account → refused, not promoted, `emailVerifiedAt` still null; verified account with wrong password → refused; verified account + right password without `--promote-existing` → refused with a hint; with the flag → promoted, password kept, audited `user.super_admin_granted { created: false }`; `--password-stdin` works; the e2e seeding helper (`apps/web/e2e/helpers/super-admin.ts`) passes the flag and still works; the runbook documents the rule.

### F3 — Per-service environment on staging

- **Threat.** The web container (the only one exposed to the internet) holds every secret of the platform; the api holds BYPASSRLS credentials; a container compromise or a leaked `docker inspect` exposes everything.
- **Decision.** `.env.staging` stays the single file on the host but is used **only for compose interpolation** (`--env-file`); each service lists its variables explicitly under `environment:` with `${VAR:?}`. Allocation: `migrate` → `DATABASE_URL_SYSTEM`; `api` → `DATABASE_URL`, `REDIS_URL`, `WEB_ORIGIN`, `JWT_SECRET`, `TOTP_ENCRYPTION_KEY`, `SMTP_URL`, `EMAIL_FROM`, `SMS_PROVIDER`, `HIBP_ENABLED`, `COOKIE_SECURE`, `RATE_LIMIT_*`, `TRUST_PROXY_HOPS`, `LOG_LEVEL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `PORT`, `APP_ENV`, `NODE_ENV`; `worker` → `DATABASE_URL_SYSTEM`, `REDIS_URL`, `SMTP_URL`, `EMAIL_FROM`, `WEB_ORIGIN`, `LOG_LEVEL`, `WORKER_PORT`, `APP_ENV`, `NODE_ENV`; `web` → `API_URL`, `PORT`, `APP_ENV`, `NODE_ENV` (no secret at all); `postgres`/`minio` unchanged. `DATABASE_URL_SYSTEM` becomes **optional** in the API env schema (only tests and the CLI's `systemPrisma()` need it). App services also get `read_only: true` with `tmpfs` for `/tmp` (and the web's `.next/cache`), `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `init: true`.
- **Acceptance.** A unit test parses `infra/compose.staging.yml` and asserts: no service uses `env_file`; `web` has no variable matching `/SECRET|PASSWORD|KEY|TOKEN|DATABASE_URL|REDIS_URL|SMTP_URL/`; `api` has neither `DATABASE_URL_SYSTEM` nor `POSTGRES_PASSWORD` nor `S3_*`; `worker` has neither `JWT_SECRET`, `TOTP_ENCRYPTION_KEY` nor `DATABASE_URL`; every app service is `read_only` with `cap_drop: [ALL]`. The API boots without `DATABASE_URL_SYSTEM`; the staging runbook lists the allocation.

### F4 — Deploy workflow: pinned host key and pinned actions

- **Threat.** Without a known host fingerprint the deploy job accepts any SSH server at `STAGING_SSH_HOST` (DNS/BGP hijack → the private key is used to authenticate to an attacker who then receives the compose file and GHCR token). Mutable action tags let a compromised upstream tag run arbitrary code with the repo's secrets.
- **Decision.** `appleboy/ssh-action` and `scp-action` get `fingerprint: ${{ secrets.STAGING_SSH_FINGERPRINT }}` (SHA256 host key fingerprint, obtained once with `ssh-keyscan -t ed25519 <host> | ssh-keygen -lf -`); the "Check deploy secrets" step treats it like `STAGING_SSH_HOST/USER/KEY`: when any of the four is missing the deploy job **skips with a notice naming the missing secret** — it never deploys without the fingerprint (owner, Q4: the secret is optional, the skip is the documented behaviour until the owner adds it). Every `uses:` in every workflow is pinned to a 40-hex commit SHA with a `# vX.Y.Z` comment; a repo test fails on any unpinned `uses:`; `.github/dependabot.yml` keeps the SHAs current (`github-actions` weekly; `npm` weekly, grouped minor/patch, limit 5 open PRs).
- **Acceptance.** `packages/config/infra/workflows.test.ts` passes (every `uses:` matches `@[0-9a-f]{40}`); the deploy workflow skips with a notice when `STAGING_SSH_FINGERPRINT` is missing and the staging runbook documents that skip and how to obtain the value (the procedure is the same for today's local staging host and for the OVHcloud production target); `actionlint` passes on all workflows (run in the security workflow, F10).

### F5 — Step-up authentication for 2FA setup and disable

- **Threat.** A session cookie obtained without the password (XSS, unattended device) can enrol an attacker's authenticator (then hold recovery codes) or disable TOTP (with the device at hand). Password change already requires the current password; 2FA, which protects the same account, does not.
- **Decision.** `POST /auth/2fa/setup` takes `{ password }`; `POST /auth/2fa/disable` takes `{ otpCode, password }`. Both verify the password through the existing `ReauthLimiter.attempt/succeeded` (5 wrong per 15 min → `429 RATE_LIMITED`, shared with password/email change) and `verifyPassword`; a wrong password → `401 INVALID_CREDENTIALS` and an audit row `auth.reauth_failed { purpose: '2fa_setup' | '2fa_disable' }`. The confirmation step (`POST /auth/2fa/verify` without challenge) is unchanged: it proves possession of the freshly enrolled seed and happens seconds after the step-up. The forced-setup flow (AC-AUTH-05) asks the password again on the setup page — accepted (standard step-up). Web: the setup page gains a password field before the QR is requested; the disable dialog gains a password field. OpenAPI regenerated; FR/AR/EN keys added.
- **Acceptance.** API: setup/disable without `password` → `422 VALIDATION_FAILED`; wrong password → `401 INVALID_CREDENTIALS` + audit row, nothing changed (no pending seed, TOTP still on); 6 wrong passwords → `429`; right password → previous behaviour. Web e2e: the AC-AUTH-05 UI flow and the settings disable flow pass with the password step; the super-admin seeding helper passes the password.

### F6 — Reject placeholder secrets outside development

- **Threat.** `.env.staging` is started from `.env.example` (runbook); a forgotten `JWT_SECRET=dev-only-…` lets anyone forge access tokens; the TOTP key from the repo decrypts every seed; `COOKIE_SECURE=false` sends cookies in clear; `WEB_ORIGIN=http://…` makes CORS and links non-TLS.
- **Decision.** `EnvSchema` (API) adds a `superRefine` applied when `APP_ENV !== 'development'`: `JWT_SECRET` and `TOTP_ENCRYPTION_KEY` must not be in `PLACEHOLDER_SECRETS` (the `.env.example`, CI and test-fixture values, listed in `apps/api/src/config/placeholders.ts`) and `JWT_SECRET` must have ≥ 3 distinct character classes; `DATABASE_URL` (and `DATABASE_URL_SYSTEM` when set) must not use the `app` password of `init.sql`; `COOKIE_SECURE` must be `true`; `WEB_ORIGIN` must be `https:`. `HIBP_ENABLED` stays a free choice in every environment (owner, Q2: not mandatory in production; no startup rule on it). The worker schema gains `APP_ENV` (same enum, default `development`) and the same checks on `DATABASE_URL_SYSTEM`, `WEB_ORIGIN`. Error messages name the variable and say "generate a real value (openssl rand …)". Tests keep running with `APP_ENV=development`/unset.
- **Acceptance.** `env.spec.ts`: each placeholder rejected under `staging` and `production`, accepted under `development`; `COOKIE_SECURE=false` + `WEB_ORIGIN=http://` rejected under staging; a well-formed staging env passes; `HIBP_ENABLED=false` is accepted under `production`. Worker `env.test.ts` equivalent. The test that asserted the `.env.example` TOTP key is accepted is rewritten to assert it is accepted **only** in development.

### F7 — Exactly one OWNER per workspace, race-free transfer

- **Threat.** Concurrent `transfer-ownership` + member removal/role change (or two transfers) can leave a workspace with no active OWNER (nobody can delete/transfer; AC-GDPR-04 deadlock) or, after a future code change, two.
- **Decision.** (1) Migration `one_owner_per_workspace`: hand-written partial unique index `membership_owner_per_workspace_key ON membership(workspace_id) WHERE role = 'OWNER'` (Prisma cannot express it; `migrate:check` ignores hand-written statements, as for `workspace_personal_owner_key`). (2) `transferOwnership` locks the two membership rows (`SELECT … FOR UPDATE` inside `withTenantTx`, after `lockWorkspace`), re-reads under lock (caller still ACTIVE OWNER and `workspace.ownerUserId`, target still ACTIVE ADMIN), demotes **then** promotes in that order (the index allows only one OWNER at any instant), updates `ownerUserId` — all in the transaction. (3) `MembersService.update` and `remove` make their conditional `updateMany` include `role: current.role` (and `remove` additionally `role: { not: 'OWNER' }`), so a membership promoted concurrently is never changed/removed (`count !== 1` → `404`/`409` as today). (4) Invariant helper in tests: exactly one `OWNER` membership per workspace, `ACTIVE`, equal to `workspace.ownerUserId`.
- **Acceptance.** `packages/db` schema test: a second OWNER row in one workspace fails with the unique violation; two OWNERs in different workspaces are fine. API tests (real concurrency with `Promise.all` over the HTTP app): transfer ∥ remove(target), transfer ∥ demote(target → TEACHER), transfer(A→B) ∥ transfer(A→C), transfer ∥ transfer-back — after each, the invariant holds and the HTTP outcomes are one of the documented pairs (one `204`, the other `404`/`409`/`422`/`403`). `pnpm db:migrate:test` and `migrate:check` green.

### F8 — Isolation suite: foreign ids, inactive members, read-only states, admin routes

- **Threat.** The guarantee « 404 for non-members » does not cover the more common bug: an ACTIVE member of A reaching B's rows by id (path, body, cursor) through a route of A; or a write that should be refused by state (`423`, `403 MEMBERSHIP_INACTIVE`) slipping through on a route nobody tested.
- **Decision.** Extend `apps/api/test/isolation/` with route-enumerated scenarios on top of the existing two: (a) **foreign ids** — every tenant route with an extra path param is called by an ACTIVE OWNER of A with the corresponding **real** id from B (a `FOREIGN_PARAMS` table in `isolation/fixtures.ts` maps param name → fixture getter; a route whose param has no fixture fails the suite with "add a fixture"), expecting `404` (`422 VALIDATION_FAILED` for cursors); (b) **foreign bodies** — a `FOREIGN_BODIES` table gives, per write route with id-bearing bodies (`assignments`, `abuse-reports` create/update, `transfer-ownership`, `members/:uid`), a body referencing B's ids → never `2xx`; every write route must be in the table or in `BODYLESS_WRITE_ROUTES` (reviewed list), else the suite fails; (c) **inactive membership** — every tenant route called by a `PENDING_APPROVAL` and a `SUSPENDED_CONSENT_REVOKED` member → `403 MEMBERSHIP_INACTIVE`; (d) **read-only states** — every write route on a SUSPENDED and a DELETING workspace by its OWNER → `423 WORKSPACE_SUSPENDED`, every read route → not `423`; (e) **platform console** — every `/admin/*` route → `403 PERMISSION_DENIED` for an ACTIVE org OWNER (no 404 masking there: the console's existence is public). `TENANT_ROUTE_EXEMPTIONS` keeps its contract (a reason per entry, code-reviewed).
- **Acceptance.** The new scenarios pass on the current routes without exemptions (any failure found is a bug to fix in the same task, with its own regression test); the runbook section "Tenant isolation suite" documents the five scenarios and the fixture tables.

### F9 — nodemailer upgrade

- **Decision.** `nodemailer@10.1.2` pinned exactly in `packages/providers`; `@types/nodemailer` removed (v10 ships types). `smtpTransportOptions` keeps its contract (URL → options; `requireTLS` outside local hosts; timeouts). The root `package.json` gains `pnpm.auditConfig.ignoreGhsas` for advisories that cannot be fixed without a major upgrade of a transitive owner (today: `deepmerge-ts` via `prisma>@prisma/config`, fixed only by Prisma 7 — listed with its GHSA and a reason), so the CI audit gate (F10) is meaningful.
- **Acceptance.** `pnpm --filter @nibras/providers test` green (smtp options, templates), API/worker e2e email tests green (Mailpit path through `InMemoryEmailProvider` unchanged; one manual Mailpit check in the task); `pnpm audit --prod --audit-level=high` exits 0.

### F10 — Security scanning in CI (pragmatic)

- **Decision.** New `.github/workflows/security.yml` (PR, push to `main`, weekly schedule): `audit` (`pnpm audit --prod --audit-level=high`, blocking; a full non-blocking summary as a second step), `dependency-review` (PRs, `fail-on-severity: high`), `codeql` (javascript-typescript, default query pack), `gitleaks` (`gitleaks/gitleaks-action` with `GITHUB_TOKEN` only — the repo `github.com/smayros-dev/nibras` is on a personal account, so no `GITLEAKS_LICENSE` and no binary fallback job, owner Q3; `.gitleaks.toml` allow-lists `.env.example` and the CI dummy values by path/regex), `trivy-config` (Dockerfiles + compose misconfiguration, HIGH/CRITICAL), `actionlint`. In `ci.yml` the `images` job builds each image with `load: true`, runs `infra/docker/verify-image.sh` (F11) and `trivy image` (HIGH/CRITICAL, `ignore-unfixed`, exit code 1), **then** pushes — a vulnerable or fat image never reaches GHCR. Every new action pinned by SHA (F4). CodeQL and secret scanning also exist as GitHub-side settings; the workflow makes them repo-controlled and PR-blocking.
- **Acceptance.** All jobs green on the branch (findings surfaced by the first run are fixed or allow-listed with a reason in the same task); `permissions` are least-privilege per job; the local-dev runbook's CI table lists the new jobs.

### F11 — Slim, hardened runtime images

- **Decision.** api/worker Dockerfiles: builder runs `pnpm prune --prod` after the build and deletes sources, tests and tooling (`apps/*/src`, `apps/*/test`, `packages/*/src`, `**/*.tsbuildinfo`, `.turbo`, `*.config.*`); the runner copies the pruned tree. `prisma` (CLI) moves from `devDependencies` to `dependencies` of `@nibras/db` because the api image runs `prisma migrate deploy` (`nibras-entrypoint migrate`) — the only build-time tool that is also a runtime tool. `infra/docker/verify-image.sh <image>` asserts: runs as uid 1001, no `typescript`/`vitest`/`eslint`/`@nestjs/cli`/`@swc/core` in any `node_modules`, no `src/` under `apps/` or `packages/`, `node -e "require('@nibras/db'); require('@nibras/contracts')"` resolves from `apps/<app>`, and the health endpoint answers when started with dummy env (api: `node apps/api/dist/main.js` needs a DB → skip the boot check for api/worker; check `--version`-style module resolution only). `compose.staging.yml` gets the read-only/cap-drop settings (F3). Expected: api/worker images drop from ~1 GB to a few hundred MB (recorded in the runbook after the first CI build).
- **Acceptance.** `verify-image.sh` passes for the three images in CI before push; `docker run … nibras-api migrate` still works (CLI present); `docker run … nibras-worker` still boots against the local stack (runbook recipe); `pnpm --filter @nibras/db migrate:check` unaffected.

### F12 — Abuse-report notifications as a worker job

- **Decision.** `POST …/abuse-reports` stores the report, writes the audit row, then enqueues one job `abuse.report_created { reportId }` on `notifications` (`jobId = abuse:{id}:notify`, `attempts: 5`, exponential backoff) — enqueue failure is logged with the report id and does not fail the request (the report exists; the super-admin queue shows it). The worker processor computes the recipients exactly as today (acknowledgement to the reporter; `abuse.new_report` to org ACTIVE OWNER/ADMIN minus reporter and reported user; super-admins when not an organisation, for `MINOR_SAFETY`, when a handler is the reported user, or when no handler is left), sends sequentially, records `sentTo` in the job progress so a retry never emails twice, and fails the job if any send failed (BullMQ retries). The shared link builders move to `@nibras/contracts` (`abuseReportLinks`). `AbuseReportsService` no longer depends on `EMAIL_PROVIDER`.
- **Acceptance.** API test: creating a report records exactly one `notifications` job with `{ reportId }` and sends **no** email inline; the five email-matrix tests move to `apps/worker/test/abuse.e2e-spec.ts` with the same expectations (recipients, exclusions, links per locale, retry idempotence); `MINOR_SAFETY` still also enqueues the 24 h reminder.

## 3. Verified and deliberately not changed

- **CSRF.** Auth cookies are `SameSite=Lax` + `httpOnly` (`apps/api/src/auth/cookies.ts:14-16`), CORS is restricted to `WEB_ORIGIN` with credentials (`app.setup.ts:25`), every mutation takes a JSON body validated by zod, and the refresh cookie is path-scoped to `/api/v1/auth`. A cross-site form POST carries no Lax cookie; a cross-origin `fetch` with credentials is refused by CORS and would not carry the cookie either. An `Origin`/`Sec-Fetch-Site` check would be defence in depth only; not in scope (noted as a follow-up).
- **Rate limits on auth.** Global anon 60/min per IP and user 600/min (`rate-limit.module.ts`), login throttle (5/min per ip+email, 15 min lock after 10), reauth limiter on password/email change (and on 2FA after F5), forgot-password 3/h per email (`password-reset.service.ts:31-32`), email-change 3/h, phone OTP windows — PRD §8.1.2 is met.
- **Cookie flags, HSTS, CSP, frame-ancestors.** Done in SP1/SP1.5 (`cookies.ts`, `apps/web/src/lib/security-headers.ts`, helmet in `app.setup.ts`).
- **Super-admin cross-tenant reads** are audited per query (`crossTenantDb({ reason: 'super_admin' })`).
- **Dev-only audit advisories** (`vitest`/`tinypool`, `braces` via `@next/eslint-plugin-next`, `esbuild` via `tsup`): not shipped; the CI gate audits `--prod`. They are tracked by Dependabot (F4), not fixed here.

## 4. Decisions

| # | Decision | Why | Alternatives considered |
|---|---|---|---|
| D1 | Partial unique index on `role = 'OWNER'` + row locks, no trigger | One statement enforces "at most one"; "at least one" is kept by the service under locks and asserted by tests; a constraint trigger would hide logic in SQL that Prisma's diff cannot see. | Deferred constraint trigger; app-only locks (the removal race needs the DB to refuse the second OWNER). |
| D2 | Step-up by password, not by TOTP, for 2FA setup/disable | Setup happens before any TOTP exists; the password is the factor the attacker with a stolen cookie lacks; same limiter as password change. | TOTP-only disable (already the case; does not cover the stolen-device case); session age (`auth_time`) window — no such claim in the JWT today. |
| D3 | Promotion requires `--promote-existing` + verified email + password proof | Removes the pre-hijack without forbidding the legitimate "promote my own verified account" path the e2e suite uses. | Create-only CLI (breaks the e2e helper and the runbook's idempotence); interactive confirmation (CLI runs non-interactively in CI). |
| D4 | Compose `environment:` per service from one `--env-file` | No new secret store; the host file stays `600`; each container sees only its allocation. | Docker secrets (compose file-based secrets need per-secret files and app changes to read `*_FILE`); separate env files per service (four files to keep in sync). |
| D5 | `prisma` CLI as a runtime dependency of `@nibras/db` | The api image runs `migrate deploy`; keeping it a devDependency would require a second install stage or a separate migrator image. Cost: ~15 MB in the worker image too. | Dedicated `nibras-migrate` image (fourth CI matrix entry, fourth GHCR package); `pnpm deploy` (its generated-client layout is not guaranteed). |
| D6 | Notifications on BullMQ with progress-based idempotence | Same pattern as the reminder job; retries without duplicate emails; the request no longer waits on SMTP. | Outbox table (more schema; SP7 "notifications" may introduce one). |
| D7 | Security workflow separate from `ci.yml` | Different triggers (schedule), different permissions (`security-events: write`), does not slow the PR gate; image scan stays in `ci.yml` because it needs the built image. | One big workflow. |
| D8 | Actions pinned by SHA + Dependabot | GitHub's own guidance; Dependabot keeps the pins fresh. | Tags (mutable), `@vN` with `allowed_actions` policy (org setting, not repo-controlled). |
| D9 | Reporter identity in a separate `AdminAbuseReportSchema`, absent (not `null`) from the org schema | Owner ruling Q1: org handlers never learn who reported; a key that does not exist cannot be rendered by a future org UI by mistake, and the contract makes the two audiences explicit. | `reporter: null` for org handlers (same shape, one more thing to remember); a `?includeReporter` query gated by role (leaks by misconfiguration). |

## 5. API contract changes

- `POST /auth/2fa/setup`: body `{ password }` (was none). `POST /auth/2fa/disable`: body `{ otpCode, password }` (was `{ otpCode }`). Both: `401 INVALID_CREDENTIALS`, `429 RATE_LIMITED` added. OpenAPI regenerated.
- Audit actions added: `auth.reauth_failed`. Audit `abuse_report.created.after` loses `reporterUserId`.
- `GET /workspaces/{wid}/abuse-reports`, `GET`/`PATCH /workspaces/{wid}/abuse-reports/{id}`: the response items lose `reporter` (`AbuseReportSchema`, org handlers — Q1). `GET /admin/abuse-reports`, `GET`/`PATCH /admin/abuse-reports/{id}`: unchanged shape, now typed `AdminAbuseReportSchema` / `AdminAbuseReportsPageSchema` (super-admins keep `reporter`). `GET /me/abuse-reports` unchanged. OpenAPI carries no response schemas for these routes (DTOs only), so the generated client is unaffected; the web admin components import the `Admin*` types.
- Queue job added: `notifications` / `abuse.report_created` `{ reportId }`.
- No change to error codes, permissions, cookie design, consent versions.
