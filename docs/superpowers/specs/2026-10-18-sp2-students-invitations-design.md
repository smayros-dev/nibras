## 1. Why this sub-project

SP1 shipped accounts, workspaces, memberships and the permission guard, but no way for anyone other than a self-registered teacher to get into a workspace: the e2e suite still inserts memberships with `psql` (`apps/web/e2e/helpers/seed.ts` `addOrgMember`), `MembershipService.addMember` has no caller, `MembersPanel` shows « Les élèves rejoignent par invitation (prochaine version) », and the onboarding item « Inviter mes étudiants » is a _Bientôt_ badge. SP2 is the first sub-project that puts students (often minors) into the product, so it also carries the per-workspace parental-consent flow (D-O5) that SP3+ gate on (`GUARDIAN_CONSENT_REQUIRED`). SP3 (courses) and SP5 (sessions) both depend on it (PRD §18).

PRD §18 row 2: `Invitation`, `InviteLink`, `GuardianLink`, consentement parental (page publique), import CSV (job), liste/profil étudiant (squelette, enrichi ensuite), retrait, notifications d'invitation (email minimal — SP7 généralise). DoD: AC-INV-01…13, AC-SAFE-06; emails FR/AR/EN nommant l'espace; job d'expiration des consentements (par espace, sans purge).

## 3. Data model (`packages/db/prisma/schema.prisma`, migration `<ts>_students_invitations`)

All four new tables are 🏢 tenant tables: `workspaceId` mandatory, appended to `TENANT_MODELS`, RLS `ENABLE` + `FORCE` + policy `tenant_isolation` copied from `20261011095737_rls_and_audit_privileges` (hand-written section). Column mapping follows SP1 (`@map` snake_case, `@@map` singular table names, `uuid(7)` ids, `timestamptz`).

```text
enum InvitationStatus    PENDING | ACCEPTED | EXPIRED | REVOKED                (§11.1)
enum InviteLinkStatus    ACTIVE | DISABLED | EXHAUSTED | EXPIRED               (§11.1)
enum GuardianLinkStatus  PENDING | ACTIVE | REFUSED | REVOKED                  (§11.1 + REFUSED, see D4)
enum GuardianRelationship PARENT | LEGAL_GUARDIAN | OTHER                     (§8.3.5 « lien de parenté »)
enum ImportStatus        QUEUED | RUNNING | COMPLETED | FAILED

Invitation 🏢  (@@map "invitation")
  id, workspaceId, email citext, role MembershipRole (STUDENT | TEACHER | ADMIN only, service rule)
  firstName?, lastName?, guardianEmail citext?, birthDate date?
  tokenHash @unique, expiresAt, status InvitationStatus
  invitedByUserId, message? (≤ 500), courseIds uuid[] (default []), teacherUserId?  (org: assignment at acceptance)
  acceptedByUserId?, acceptedAt?, revokedAt?, resentCount int default 0, lastSentAt
  createdAt, updatedAt
  @@index([workspaceId, status]), @@index([workspaceId, email]), @@index([invitedByUserId])
  hand-written: CREATE UNIQUE INDEX invitation_pending_per_email_key ON invitation(workspace_id, email) WHERE status = 'PENDING'

InviteLink 🏢  (@@map "invite_link")
  id, workspaceId, code text @unique (8 chars, alphabet ABCDEFGHJKLMNPQRSTUVWXYZ23456789, stored upper-case)
  label? (≤ 80), role = STUDENT (column kept for §11.2 parity, service forces STUDENT)
  createdByUserId, teacherUserId?, courseIds uuid[] default []
  requiresApproval bool, maxUses int, usesCount int default 0, expiresAt?, status InviteLinkStatus
  createdAt, updatedAt
  @@index([workspaceId, status])

GuardianLink 🏢  (@@map "guardian_link")   — one per (student, workspace), D-O5
  id, workspaceId, studentUserId, guardianUserId? (null until the P1 guardian account), guardianEmail citext
  guardianFirstName?, guardianLastName?, relationship GuardianRelationship?
  status GuardianLinkStatus, consentId? → Consent
  consentTokenHash? @unique, consentExpiresAt?, consentSentAt?, consentResentCount int default 0   (the 14-day request link)
  sessionsViewTokenHash? @unique                                                                  (the long-lived guardian page link, §11.2 name)
  decidedAt?, revokedAt?, createdAt, updatedAt
  @@unique([studentUserId, workspaceId]), @@index([workspaceId, studentUserId]), @@index([guardianUserId]), @@index([guardianEmail])

InvitationImport 🏢  (@@map "invitation_import")
  id, workspaceId, createdByUserId, fileName (≤ 255), status ImportStatus
  rows Json          (the parsed valid rows the worker consumes: [{ line, email, firstName?, lastName?, guardianEmail?, birthDate?, courseCodes: string[] }])
  report Json        (per-line outcome, filled progressively: [{ line, email, outcome, message? }])
  totalRows int, validRows int, processedRows int default 0, createdCount int default 0, failedCount int default 0
  error?, startedAt?, finishedAt?, createdAt, updatedAt
  @@index([workspaceId, createdAt(sort: Desc)])
```

`Consent` is unchanged: a `GUARDIAN_PARENTAL` row carries `userId = student`, `grantedByEmail = guardian`, `workspaceId`, `version = GUARDIAN_CONSENT_VERSION` (`'guardian-2026-10'`, `@nibras/contracts`), `ip`, `userAgent`, `granted = true`; revocation sets `revokedAt`. The partial unique index `consent_guardian_parental_active_key` (SP1) guarantees one active consent per (student, workspace). A **refusal writes no `Consent` row** (D4). `Membership` is unchanged (statuses `PENDING_APPROVAL`, `PENDING_GUARDIAN_CONSENT`, `SUSPENDED_NO_CONSENT`, `SUSPENDED_CONSENT_REVOKED`, `REJECTED` already exist).

`packages/db/src/tenant.ts` gains `CROSS_TENANT_LOOKUP_KEYS: Partial<Record<TenantModel, readonly string[]>>` = `{ Invitation: ['tokenHash'], InviteLink: ['code'], GuardianLink: ['consentTokenHash', 'sessionsViewTokenHash'] }`: `crossTenantDb()` accepts a top-level equality filter on one of those unique secret columns as the "always filtered" condition of PRD §13.3, next to `userId` / `id`. A public token route resolves the workspace with one such lookup, then does every write inside `withTenantTx(workspaceId, …)` (RLS applies to the writes).

## 4. Flows

### 4.1 Email invitation (student or staff)

```text
POST /workspaces/{wid}/invitations  { email, role = STUDENT, firstName?, lastName?, guardianEmail?, birthDate?, message?, courseIds?, teacherUserId? }
  guard chain: JWT → gates → workspace → @RequirePermission('student.invite') → @RequireVerifiedTeacher()
  service: role ∈ {TEACHER, ADMIN} → workspace must be ORGANIZATION and currentGrant('workspace.staff.manage') === 'all' (else 403 / 422 INVITATION_ROLE_NOT_ALLOWED)
           live membership of that email (any status but REMOVED/REJECTED) → 409 ALREADY_MEMBER   (covers « un professeur n'est pas étudiant du même espace »)
           PENDING invitation for (wid, email) → 409 INVITATION_PENDING (details.invitationId)        (partial unique index decides under races)
           teacherUserId (org admins only): must be an ACTIVE teaching member, else 422; a TEACHER inviter is the implicit teacherUserId
           token = generateOpaqueToken(); row { tokenHash, expiresAt = now + 7 d, status PENDING, lastSentAt = now }
  after commit: audit invitation.created { email, role, expiresAt }; email invitation.received_student | invitation.received_staff
                (inline, failure logged, « Renvoyer » covers it — same pattern as EmailVerificationService.send)
  → 201 InvitationSummary (never the raw token)
```

- `GET /workspaces/{wid}/invitations?status&role&q&cursor&limit` (`student.invite`): scope `own` (organisation TEACHER) → only rows he created; staff rows need `workspace.staff.manage`. Status is **derived**: a stored `PENDING` whose `expiresAt < now` is served as `EXPIRED` (the daily job flips the stored value, §7).
- `POST …/invitations/{id}/resend` (`student.invite`, verified teacher): allowed from `PENDING` / `EXPIRED`; `lastSentAt > now − 10 min` → `429 RATE_LIMITED` (`details.retryAfterS`, AC-INV-04); new token, old hash replaced (the old link answers `410 TOKEN_INVALID`), `expiresAt = now + 7 d`, `resentCount + 1`, status `PENDING`; audit `invitation.resent`.
- `DELETE …/invitations/{id}` → `REVOKED`, `revokedAt`; audit `invitation.revoked`; the link answers `410 INVITATION_REVOKED` (AC-INV-05).

### 4.2 Acceptance (public, `@OptionalAuth()`)

```text
GET  /invitations/{token}          → InvitationPreview { workspace { name, type }, inviter { firstName, lastName }, role, emailMasked, accountExists,
                                      viewer: 'ANONYMOUS' | 'MATCH' | 'MISMATCH' (the signed-in user vs the invited address), requiresBirthDate, guardianEmailPrefilled, expiresAt }
                                     unknown → 410 TOKEN_INVALID · expired → 410 INVITATION_EXPIRED · revoked → 410 INVITATION_REVOKED · accepted → 410 INVITATION_ALREADY_ACCEPTED
POST /invitations/{token}/accept   body (discriminated on `mode`):
   { mode: 'REGISTER', firstName, lastName, password, locale, timezone, birthDate?, guardianEmail?, acceptTerms: true, acceptPrivacy: true }   — anonymous, no account for that email
   { mode: 'JOIN', birthDate?, guardianEmail? }                                                                                                — signed in as the invited address
```

Rules (D-P18, §8.1.1, §8.3.2, §8.3.5):

1. Signed in with another address → `403 INVITATION_EMAIL_MISMATCH` (`details.emailMasked`); the page offers « Se déconnecter et continuer avec {email} » (AC-INV-02). Anonymous `REGISTER` while an account exists → `409 EMAIL_TAKEN`; the page shows « Se connecter » with `next=/invite/{token}` (AC-INV-03).
2. `STUDENT` role: `birthDate` is mandatory (from the invitation, the account, or the body — else `422 BIRTH_DATE_REQUIRED`). `isMinor(birthDate, now)` (< 18, D-P3) → `guardianEmail` mandatory (invitation or body — else `422 GUARDIAN_EMAIL_REQUIRED`), must differ from the student's email (`422 GUARDIAN_EMAIL_INVALID`).
3. One `withTenantTx(wid)`: lock the invitation row (`SELECT … FOR UPDATE`), re-check `PENDING` and unexpired and the email; `REGISTER` → create `User` with **`emailVerifiedAt = now`** (the link proves control of the mailbox, D2), `TERMS` + `PRIVACY` consents, `birthDate`; `MembershipService.addMember(…, tx)` with status `ACTIVE` (adult student, TEACHER, ADMIN) or `PENDING_GUARDIAN_CONSENT` (minor) and `invitedByUserId`; minor → `GuardianLink { status PENDING, guardianEmail, consentTokenHash, consentExpiresAt = now + 14 d }`; organisation + teaching inviter or `teacherUserId` → `TeacherStudentAssignment`; invitation → `ACCEPTED` (`acceptedByUserId`, `acceptedAt`).
4. After commit: `added.audit()` (`member.added`), audit `invitation.accepted`, `guardian.consent_requested` (minor), emails `guardian.consent_requested` (to the guardian, names workspace and teacher) and `invitation.accepted` (to the inviter — minimal stand-in for the in-app `INVITATION_ACCEPTED` of SP7, Q6), `InvitationAcceptedEvent` (EventEmitter2, SP7/SP10 hooks). `REGISTER` → session cookies set like `POST /auth/register` (`SessionService.createSession` + `setAuthCookies`).
5. A `TEACHER` / `ADMIN` accepted this way gets **no** PERSONAL workspace (D-O7; `POST /me/personal-workspace` exists since SP1) and is sent to `/app/settings/verification` by the web (phone OTP + code of conduct, AC-SAFE-01 unchanged). An `ADMIN` is subject to mandatory 2FA from the next request (SP1 `AccountGatesGuard`).
6. Response `201 { user: MeUser, workspace: { id, name }, membershipStatus }`.

The second workspace of an already-consented minor restarts the whole cycle for that workspace (AC-INV-13): a new `GuardianLink` row (unique per `(student, workspace)`), a new consent email naming the new workspace, the earlier `Consent` untouched.

### 4.3 Group link / code (`InviteLink`)

- `POST /workspaces/{wid}/invite-links` (`student.invite`, verified teacher) `{ label?, requiresApproval? (default: `workspace.type === 'ORGANIZATION'`), maxUses? (default 50, 1–1000), expiresAt? (default now + 30 d, ≤ 365 d), courseIds?, teacherUserId? }` → code from `randomBytes` mapped onto the 32-char alphabet (retry on `P2002`); `GET …/invite-links`, `PATCH …/invite-links/{id}` `{ label?, status: 'ACTIVE' | 'DISABLED', maxUses?, expiresAt?, requiresApproval? }`, `DELETE …/invite-links/{id}` (= `DISABLED`; rows are kept for the audit trail). Audit `invite_link.created` / `invite_link.updated`.
- Public `GET /join/{code}` (code upper-cased, `@OptionalAuth()`) → `JoinPreview { workspace, teacher, requiresApproval, viewer, status }`; exhausted / expired / disabled → `410 INVITE_LINK_EXHAUSTED | INVITE_LINK_EXPIRED | INVITE_LINK_DISABLED`; unknown → `404 NOT_FOUND`. Failed lookups are counted per IP (`TokenAttemptLimiter`, 20 / 10 min → `429`).
- Public `POST /join/{code}/accept` with the same `REGISTER` / `JOIN` bodies plus a mandatory `email` in `REGISTER` (the code is not bound to an address, D-P18). Inside `withTenantTx`: lock the link row, re-check status / expiry / `usesCount < maxUses`, `usesCount + 1` (`= maxUses` → `EXHAUSTED`, AC-INV-08's third student gets `410 INVITE_LINK_EXHAUSTED`); a `REGISTER` account is created **unverified** with an `EMAIL_VERIFY` token and the SP1 verification email (the code proves nothing about the mailbox, D2); membership status: `requiresApproval` → `PENDING_APPROVAL`, else minor → `PENDING_GUARDIAN_CONSENT` (+ `GuardianLink` + consent email), else `ACTIVE`. Audit `invite_link.used`, `member.added`. A user already a member → `409 ALREADY_MEMBER`.
- Approval queue: `POST /workspaces/{wid}/members/{uid}/approve` / `…/reject` (`student.invite`; scope `own` → only members whose `invitedByUserId` is the caller): membership must be `PENDING_APPROVAL` (else `409 MEMBERSHIP_NOT_PENDING`); approve → `ACTIVE`, or, for a minor without an active consent, `PENDING_GUARDIAN_CONSENT` with the consent email sent **now** (D5: a guardian is never asked for a student the teacher may still refuse); reject → `REJECTED`, `removalReason`. Audit `member.approved` / `member.rejected`; emails `join.approved` / `join.rejected` to the student.

### 4.4 Guardian consent (public, `@Public()`)

```text
GET  /guardian-consent/{token}    → GuardianConsentPreview { student { firstName, lastName }, workspace { name, type }, teacher { firstName, lastName }, expiresAt, version, noticeUrl }
                                     unknown / replaced → 410 TOKEN_INVALID · expired → 410 CONSENT_LINK_EXPIRED · already decided → 410 CONSENT_ALREADY_DECIDED
POST /guardian-consent/{token}    { decision: 'GRANT' | 'REFUSE', guardianFirstName, guardianLastName, relationship, acceptNotice: true (GRANT) }
```

- `GRANT` (AC-INV-10): one `withTenantTx(wid)`: lock the `GuardianLink` row; `Consent { userId: student, grantedByEmail, type GUARDIAN_PARENTAL, version, workspaceId, ip, userAgent, granted: true }`; link → `ACTIVE`, `consentId`, `decidedAt`, names + relationship, `consentTokenHash = null` (single use), `sessionsViewTokenHash = hash(new token)`; membership `PENDING_GUARDIAN_CONSENT | SUSPENDED_NO_CONSENT | SUSPENDED_CONSENT_REVOKED → ACTIVE` (`joinedAt` set if null). After commit: audit `guardian.consent_granted`; emails `guardian.consent_confirmation` (to the guardian: the workspace, the teacher, the link « Sessions de {prénom} » = guardian page, and the revoke action on that page), `guardian.consent_granted` (student), `guardian.consent_granted_teacher` (inviter / workspace owner); `MembershipActivatedEvent`.
- `REFUSE`: link → `REFUSED`, `decidedAt`, token cleared; membership → `SUSPENDED_NO_CONSENT`; audit `guardian.consent_refused`; emails `guardian.consent_refused` (student, teacher); `MembershipDeactivatedEvent`.
- Guardian page: `GET /guardian/{token}` → `GuardianView { student, workspace, teacher, link: { status, grantedAt, revokedAt }, sessions: [] }` (AC-SAFE-06: `sessions` lists only that workspace's sessions of that student — SP5 fills it; SP2's test asserts the empty list and that a token of workspace A never shows workspace B's data); `POST /guardian/{token}/revoke` (AC-INV-11): `Consent.revokedAt`, link → `REVOKED`, membership → `SUSPENDED_CONSENT_REVOKED` for **this workspace only**, audit `guardian.consent_revoked`, emails to student, teacher and (organisation) ACTIVE OWNER/ADMINs, `MembershipDeactivatedEvent` (SP6 disconnects rooms ≤ 60 s, SP5 cancels future participations). Nothing is purged (D-O5). `POST /guardian/{token}/grant` (re-grant after a revocation or refusal, with the same body as `GRANT`): new `Consent` row (the previous one is revoked, so the partial unique index allows it), link → `ACTIVE`, membership → `ACTIVE`.
- Resend / « relance » (AC-INV-12): `POST /workspaces/{wid}/students/{uid}/guardian/resend-consent` (`student.update`, verified teacher) and the student's own `POST /me/workspaces/{wid}/guardian/resend-consent`: allowed when the membership is `PENDING_GUARDIAN_CONSENT`, `SUSPENDED_NO_CONSENT` or `SUSPENDED_CONSENT_REVOKED`; new consent token, `consentExpiresAt = now + 14 d`, link → `PENDING` (membership unchanged until the guardian decides), `consentResentCount + 1`; `consentSentAt > now − 10 min` → `429 RATE_LIMITED`. `PATCH …/students/{uid}` with a new `guardianEmail` updates the link's email (audit `guardian.email_changed`) and resends to the new address when a decision is still pending.
- Student side: `WorkspaceContextGuard` answers `403 GUARDIAN_CONSENT_REQUIRED` (`details.status`) for `PENDING_GUARDIAN_CONSENT`, `SUSPENDED_NO_CONSENT`, `SUSPENDED_CONSENT_REVOKED` (AC-INV-09) and keeps `403 MEMBERSHIP_INACTIVE` for `PENDING_APPROVAL`; `GET /me/workspaces` items gain `guardian: { emailMasked, status, consentExpiresAt } | null`, so the web renders the waiting panel without a tenant call. Other workspaces of the student work normally (`/me/…` aggregates are per membership).

### 4.5 CSV import (§8.3.4)

```text
POST /workspaces/{wid}/invitations/import?dryRun=true   { fileName, content }   content ≤ 1 MiB (JSON body; configureApp raises the JSON limit to 1 MiB), ≤ 500 data rows (413 IMPORT_TOO_LARGE)
   → ImportPreview { totalRows, validRows, rows: [{ line, email, firstName, lastName, guardianEmail, birthDate, courseCodes, outcome: 'OK' | 'INVALID_EMAIL' | 'DUPLICATE_IN_FILE' | 'ALREADY_MEMBER' | 'ALREADY_INVITED' | 'INVALID_BIRTH_DATE' | 'INVALID_GUARDIAN_EMAIL' | 'MISSING_GUARDIAN_EMAIL' | 'UNKNOWN_COURSE_CODE' }] }
POST …/invitations/import                                 same body → 202 { importId }  (InvitationImport QUEUED, rows = the valid rows, job `invitations.import_csv` { importId, workspaceId }, jobId `import:{importId}`)
GET  …/invitations/import/{importId}                      → ImportStatus { status, totalRows, validRows, processedRows, createdCount, failedCount, report, finishedAt }
GET  …/invitations/import/{importId}/report               → text/csv (line, email, outcome, message), Content-Disposition attachment
```

Columns `email` (required), `first_name`, `last_name`, `guardian_email`, `birth_date` (`YYYY-MM-DD`), `course_codes` (`;`-separated; validated against `[]` in SP2 — any value is `UNKNOWN_COURSE_CODE` until SP3 registers course codes, the row stays valid and the codes are dropped with a warning outcome `OK_COURSES_IGNORED`). Header row required; UTF-8 with optional BOM; `,` or `;` delimiter auto-detected on the header line (`csv-parse`). A minor row (`birth_date` < 18 y) without `guardian_email` is `MISSING_GUARDIAN_EMAIL` (the invitee may still enter it at acceptance, so it is a warning: outcome `OK_GUARDIAN_AT_ACCEPT`). Exactly one import `QUEUED | RUNNING` per workspace at a time (`409 IMPORT_IN_PROGRESS`).

Worker `invitations.import_csv` (`imports` queue, attempts 3): per valid row, in its own transaction, re-checks membership / pending invitation, creates the `Invitation` (token generated in the worker — `generateOpaqueToken` from `@nibras/contracts`), then sends `invitation.received_student`, appends the row outcome to `report` and increments `processedRows` (BullMQ progress too). Two failure modes are kept apart: an **email failure** marks that row `FAILED` (the invitation exists, the teacher can « Renvoyer » it from the pending tab) and the job goes on; an **infrastructure failure** (database error, process death) fails the job and BullMQ retries it — the retry resumes at `processedRows`, and a pending invitation already created for a row counts as `ALREADY_INVITED`, so no address is ever emailed twice. End: `COMPLETED` (`finishedAt`), email `imports.completed` to the importer with the counts and the report link; audit rows `invitations.import_started` / `invitations.import_completed` (actor `SYSTEM`, `requestId = job id`); attempts exhausted → `FAILED` with `error`. AC-INV-07: 100 rows, 3 invalid emails, 2 duplicates → preview flags 5, job creates 95.

### 4.6 Students list & profile (skeleton)

- `GET /workspaces/{wid}/students?status&q&cursor&limit` (`student.read`): `STUDENT` memberships (every status but `REMOVED` / `REJECTED` unless filtered), scope `own` = `MembersService.ownScope` (assigned to or invited by the caller — AC-WS-02 for students); `StudentSummary { userId, firstName, lastName, email? (scope all), status, joinedAt, invitedByUserId, isMinor, guardian: { emailMasked | email (scope all), status, consentExpiresAt } | null, progressPercent: null, attendanceRate: null, lastActivityAt: null, courses: [] }`. Pending invitations are a separate list (`GET …/invitations?status=PENDING&role=STUDENT`); the web merges them under the « En attente » tab (§9.1).

## 9. Security & privacy

- **Tokens.** Invitation and consent tokens: 32 random bytes, base64url in the link, SHA-256 hex in the DB (`generateOpaqueToken`), single use (hash cleared or row status changed in the same transaction as the acceptance), expiry 7 d / 14 d, replaced on resend; guardian page token: same generation, long-lived, replaced at every re-grant. Invite codes: 8 characters from a 32-symbol alphabet (≈ 1.1 × 10¹²), uppercase-normalised, never ambiguous O/0/I/1. No raw token is ever stored, logged (`REDACT_KEYS` already covers `*token*`), audited or put in a job payload.
- **Rate limits.** Anonymous 60 req/min/IP (SP1) + `TokenAttemptLimiter` (10 failed token/code lookups per minute per IP on the public routes → `429 RATE_LIMITED`, Redis `hitWindow`) + per-row resend cooldowns (10 min) + one import at a time per workspace. The `TeacherVerifiedGuard` (D-O6) gates every route that sends an invitation or consent email.
- **Email binding (D-P18).** The accept route compares the invited address with the session's user (`403 INVITATION_EMAIL_MISMATCH`) and, for `REGISTER`, with the body — the email field is locked to the invitation's address server-side (the body carries no email for invitations; it does for codes).
- **Tenant isolation.** Four new 🏢 tables under RLS + `tenantDb`; public routes resolve the workspace through `crossTenantDb()` filtered by a unique secret column (`CROSS_TENANT_LOOKUP_KEYS`), then write under `withTenantTx(wid)`; the generic isolation suite (SP1.6 T6) gets `FOREIGN_PARAMS` fixtures for `:id` of invitations / invite-links / imports and `:uid` of students, and `FOREIGN_BODIES` for `teacherUserId` and `courseIds` of workspace B.
- **Minors.** Membership of a minor is never `ACTIVE` without an unrevoked `GUARDIAN_PARENTAL` consent for that workspace (checked in the accept, approve and grant paths; asserted by a service-level invariant test). Consent rows record `ip`, `userAgent`, `version`, `grantedByEmail`. Revocation / refusal / expiry only suspend the membership of that workspace; no data is purged (D-O5, AC-INV-11/12). The guardian page shows the child's data of **one** workspace only (AC-SAFE-06).
- **Account creation by link.** An email invitation creates a **verified** account (mailbox control proven by the link); a group code creates an **unverified** one that must verify (D2) — so a code never becomes a way to register under someone else's address with the gates skipped.
- **Audit.** Every mutation audited (list in §5); the reporter deny-list of SP1.6 stays untouched; invitation audit rows carry the invitee email (tenant data), never tokens.
- **Data in emails.** The consent email names student, workspace and teacher (D-O5 requirement); it carries no birth date. The guardian confirmation carries the long-lived guardian link — the email states that the link gives access to the child's session list and must not be forwarded.
- **Abuse reporter rule** (owner decision): untouched; the guardian page has no report button in SP2 (guardians have no account).

## 11. Open questions for the owner (answered 2026-10-18: defaults accepted)

- **Q1 (D11)** PRD §7 lets a teacher « Modifier les informations d'un étudiant » (🔒). SP2 limits that to invitation-stage names, the guardian email and (SP3) course assignment; once the account exists, only the student changes his name. Confirm, or ask for a per-workspace display name.
- **Q2 (D2)** Accepting an email invitation marks the address verified without a second email. Confirm.
- **Q3 (D4)** A guardian refusal is recorded on the `GuardianLink` (`REFUSED`, `decidedAt`, audit) and not as a `Consent` row. Confirm.
- **Q4 (D5)** Code + approval + minor: the consent email goes out when the teacher approves. Confirm.
- **Q5 (D6)** One long-lived guardian link (email-held bearer) serves view + revoke + re-grant; it is regenerated on every re-grant and never expires otherwise. Confirm, or ask for an expiry (e.g. 12 months, re-sent on demand).
- **Q6** `INVITATION_ACCEPTED` is an email to the inviter in SP2 (the catalogue says in-app; SP7 delivers that). Confirm the interim email.
- **Q7** Organisation ADMINs see guardian emails of every student (scope `all`); a TEACHER sees them masked except for students he invited. Confirm.
- **Q8** Legal deliverable: the « notice mineurs » (FR/AR/EN) linked from the consent page; SP2 ships a placeholder `/legal/minors` like `/legal/terms`. Owner to provide the text before any real guardian is emailed.
- **Q9** `allow_personal_workspaces` interplay: an invited TEACHER who is also, later, invited as STUDENT elsewhere is fine (different workspaces). A STUDENT invited as TEACHER in the **same** workspace is refused (`ALREADY_MEMBER`, one membership per workspace, §6.2). Confirm nothing more is expected (role upgrade = remove + re-invite).
