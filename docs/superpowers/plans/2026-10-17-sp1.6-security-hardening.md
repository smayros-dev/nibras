## Review Focus

Five failure modes the spec implies but no acceptance criterion exercises directly; each has its test in the owning task.

1. **Promotion by a verified-but-stolen account** — an account whose email was verified by its real owner, then taken over (password changed by an attacker), still verifies the attacker's password. The CLI cannot detect that; the runbook must say the operator proves *their own* password, and the test must show a password mismatch is refused even for a verified account. → T2.
2. **Step-up bypass through the confirmation route** — `POST /auth/2fa/verify` (no challenge) must still require a *pending* seed created by a password-checked `setup`; a stale pending seed from before the deploy is fine, but `verify` must never create one. → T4.
3. **Zero-owner window** — transfer demotes before it promotes; a crash between the two statements must roll back (same transaction); the removal race must be refused by `role` in the conditional update, not only by the unique index. → T5.
4. **Foreign id that is also valid locally** — a user who is a member of both A and B: `/workspaces/A/members/{uid}` must return A's membership, never B's; the foreign-id scenario must use ids that exist only in B. → T6.
5. **Retry storms** — a notification job retried 5 times with one dead recipient must email the live recipients once (`sentTo` progress), and the reporter's acknowledgement must not be re-sent. → T7.
